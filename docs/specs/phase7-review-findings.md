scenario: 1. A navigator opens case Y. In "Where is the delay?" she taps stage "Investigations" and its "Other" chip, and leaves the description box empty. 2. ### C6 [medium] (auth-session/session-revocation) src/components/board/Board.tsx:59
summary: The board's 30 s poll treats a 401 from /api/board exactly like a dropped wifi packet: it discards the response, keeps polling forever, and keeps ticking the elapsed clocks over rows that are no longer being refreshed, so a revoked or expired session never sends the browser back to /login and the screen keeps presenting frozen clinical data as live.
scenario: 1. A navigator signs in on the ward phone at 07:00 and leaves the board open on /?f=open. 2. At 14:00 an ADMIN opens Admin -> Users and unticks Active for that nurse (she has left the service). `setUserActive` runs `deleteSessionsForUser(userId)` (src/lib/admin/users.ts:206) and every Session row for her is gone. 3. The phone keeps rendering the 14:00 row set indefinitely, and because `setNow` runs before the fetch, every LOS clock and every threshold band keeps advancing, so the board looks live. fix: Distinguish an authentication failure from a transport failure. In the poll, branch on `response.status === 401` and force a full navigation to the login form (e.g. `window.location.href = '/login?expired=1'`, which the gate already recognises as the cookie-clearing path) and `clearInterval(timer)`; keep the existing swallow-and-retry behaviour only for network errors and 5xx. skeptic: The mechanism survives: Board.tsx:59 collapses every non-OK response to null, so a 401 from the revoked session is indistinguishable from a dropped packet — no redirect, no clearInterval, no staleness cue, and no other client code compensates (the only other client fetch in the repo is ExportPanel.tsx:55; there is no service worker, no visibilitychange handler, no router.refresh on the board). The board therefore keeps repainting the last payload with `now` ticking forever after an ADMIN unticks Active. Nothing prevents that path. But the claimed HIGH severity is wrong on three counts. (b) The claim's second trigger is factually refuted: resolveSessionToken slides expiresAt every 5 minutes (needsSlidingRefresh / SLIDING_REFRESH_MS), and the 30 s poll is itself a request, so an awake open board renews its own session indefinitely — plain 12 h expiry never fires on a board left open. Worth the ~4-line fix; medium, not high.

### C7 [medium] (auth-session/open-redirect) app/login/actions.ts:27
summary: `safeNext` rejects `//` and `/\` prefixes but not a `/` followed by an ASCII tab, CR or LF, and the URL parser strips those characters before resolving, so `?next=/%09//evil.example` survives validation and redirects the user off-site immediately after a successful sign-in.
scenario: 1. An attacker sends a nurse the link `https://nav.towardpcc.com/login?next=%2F%09%2F%2Fevil.example` - a genuine hospital URL on the real domain, so it survives inspection. 2. app/login/page.tsx:29 decodes `next` to the 15-character string `/<TAB>//evil.example` and renders it verbatim into the hidden input at app/login/login-form.tsx:36. 3. The nurse types her real credentials and submits. 4. `safeNext` sees `typeof value === 'string'`, length > 0, `startsWith('/')` true, `startsWith('//')` false (the second character is a tab), `startsWith('/\')` false - so it returns the value unchanged. 5. `redirect('/\t//evil.example')` at line 69 hands that string to the browser, which strips ASCII tab/CR/LF before parsing: verified locally, `new URL('/\t//evil.example', 'https://nav.towardpcc.com/login').href === 'https://evil.example/'`. The nurse lands on the attacker's page, freshly signed in and primed to re-enter her hospital password on a look-alike form. `%0A` and `%0D` work identically.
fix: Stop pattern-matching on the raw string and resolve it instead: `const u = new URL(value, 'https://placeholder.invalid'); if (u.origin !== 'https://placeholder.invalid') return '/'; return u.pathname + u.search`.
